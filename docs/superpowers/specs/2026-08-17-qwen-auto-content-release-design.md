# 通义千问自动句库发布设计

## 目标

把当前规则模板句库替换为通义千问逐批生成、独立审校的 `2026.08.3` 系统句库。流程由用户手动触发，但触发后自动完成生成、审校、质量检查、发布、测试、提交和部署，不需要把 API Key 交给 GitHub 或浏览器。

## 安全边界

- `DASHSCOPE_API_KEY` 只从腾讯云服务器的 `/etc/phrase-bank/qwen-content.env` 读取。
- GitHub Actions、Git 历史、构建产物、日志和候选内容中不得出现密钥。
- 工作流通过既有 SSH 部署凭据连接服务器；远端命令使用 `docker run --env-file` 注入密钥。
- 日志只显示类别、生成/审校阶段和进度，不输出请求头或环境变量。
- 只有手动 `workflow_dispatch` 才会调用模型并产生费用。

## 自动发布流程

1. 用户手动触发 `Generate and deploy Qwen content` 工作流，版本固定为未发布的 `2026.08.3`。
2. 工作流在服务器 `/opt/phrase-bank` 同步 `main`，确认应用目录干净且密钥文件存在、权限不宽于 `0600`。
3. 服务器使用 Node 22 临时容器运行 `npm run content:qwen -- --version 2026.08.3`。
4. 现有内容 Agent 将 600 个核心分批处理；每批先由 Qwen 生成，再用新的独立上下文审校。
5. 生成成功后，工作流从服务器取回候选 JSON 和报告。密钥文件及其他服务器数据不被复制。
6. GitHub runner 再次验证报告、内容结构、类别配额、父子关系、英文重复、句式多样性和中英语境完整性。
7. 质量门通过后运行发布器，新增 `public/content/system-content-2026.08.3.json` 并更新 `BUNDLED_SYSTEM_CONTENT_VERSION`。
8. 运行内容专项测试、全量测试、代码检查和生产构建。
9. 全部通过后由工作流提交生成文件和版本引用并推送 `main`；现有部署工作流随后自动发布到腾讯云。
10. 任一步失败都不提交、不部署，线上继续使用 `2026.08.2`。

## 内容质量要求

- 精确 600 个核心句、2,000 条总内容，维持既有六类配额。
- 每个核心句带 2–3 个相关例句，ID、父子关系及解锁顺序稳定。
- 英文为自然、实用的 A2–B2 成人口语，不允许机械占位符或整组同一开头。
- 中文必须翻译完整语境，包括 `packaging review`、`pricing` 等前置场景，而不是只翻译动作和宾语。
- 同一学习组的系统核心句优先分散到不同子主题。
- AI 审校结果仍必须通过确定性程序质量门，AI 自评不能绕过发布检查。

## 数据兼容与回滚

- `2026.08.3` 延续现有稳定句子 ID；客户端安装新版本时更新文本，但保留学习状态、复习计划、训练记录和活动会话。
- 新版本安装失败时客户端继续使用旧版本，并可在下次启动重试。
- 回滚只需把 `BUNDLED_SYSTEM_CONTENT_VERSION` 恢复为 `2026.08.2` 并重新部署；旧版本 JSON 保留。

## 并发与失败处理

- 内容生成工作流使用独立并发组，同一时间只允许一个生成任务；后发任务不取消正在付费的任务。
- Qwen 的限流、服务端错误和超时沿用有限重试，认证失败立即停止。
- 候选和报告以版本命名；同版本重复运行从安全断点继续，但发布前必须得到完整一致的最终包。
- 推送前若 `main` 已前进，工作流重新同步并重跑发布校验；不能快进时停止，不强推。
- 部署由现有串行部署并发组处理，生成工作流不直接操作运行中的容器或用户数据库。

## 验收

- 使用假 Qwen 客户端测试生成、独立审校、失败停止和敏感信息不泄露。
- 使用工作流源代码合同测试密钥只在服务器读取、候选取回范围受限、质量门早于提交。
- 新正式内容包通过 600/2,000、配额、关系、重复、多样性和完整翻译检查。
- 新版本覆盖安装测试证明旧学习状态保持不变。
- 全量测试、Lint、生产构建和性能门禁通过。
- GitHub 生成工作流与随后部署工作流均成功，线上 `2026.08.3` 文件可访问。
